`gavel lint` discovers native tool configuration and project signals, runs selected linters concurrently, and reports their findings together. Keep tool rules in the tool's native configuration; use `.gavel.yaml` for orchestration, runtime limits, and explicit tool selection.

```bash
gavel lint
gavel lint --dry-run
gavel lint golangci-lint ./pkg/parser
gavel lint --linters eslint,tsc ./web
```

## Supported tools

<DocChildren parent="lint-execution" />

| Area | Linters |
| --- | --- |
| Go | `golangci-lint` (alias `golangci`) |
| Python | `ruff`, `pyright` |
| JavaScript and TypeScript | `eslint`, `oxlint`, `tsc` (alias `typescript`) |
| React | `react-doctor`, activated by a React dependency |
| Markdown and prose | `markdownlint`, `vale` |
| Duplicate code | `jscpd` |
| Secrets | `betterleaks` (alias `secrets`) |

Detection depends on each tool's native configuration or signal, such as `tsconfig.json` or a React dependency in `package.json`. `--linters` restricts execution and rejects unknown names. `jscpd` can be enabled explicitly through project settings. Use `--dry-run` to see which commands your repository will execute.

## Scope findings and compare runs

```bash
gavel lint --changed
gavel lint --since origin/main
gavel lint --baseline .tmp/main.json
gavel lint --failed
gavel lint --failed .tmp/previous.json
gavel lint --pr 12
gavel lint --ignore "**/generated/**"
```

`--changed` reports new issues relative to `origin/main`, or `$GAVEL_CHANGED_BASE` when set. `--since` chooses another merge-base reference. These are reporting filters; a native tool may still analyze the wider project.

`--baseline` removes findings already represented in a saved report. Baseline matching uses linter, file, and rule, so moving a line does not make the same finding new. It also means multiple findings of the same rule in one file share that identity.

`--failed` selects linters and files with previous violations, using `.gavel/last.json` when no file is specified. `--pr` uses a PR's Gavel artifacts. Keep an explicit snapshot when reproducing a specific CI failure.

Explicit `--failed` and `--baseline` files must be saved snapshot objects. Standalone `gavel lint --json` exports an array for analysis; that array is not a rerun baseline. After a lint run, copy the snapshot named by `.gavel/last.json` as shown in [Reporting](/docs/reporting).

## Native fixes and AI repair

```bash
gavel lint --fix
gavel lint --ai-fix --ai-fix-max-iterations 3
```

`--fix` asks supported native tools to edit source. `--ai-fix` runs the configured `lint.fix` agent and reruns lint until clean or its iteration limit is reached. AI repair needs a configured model runtime. `-y` implies AI repair, so it is an editing operation. Run plain `gavel lint` to inspect findings first.

`--triage` is an interactive operation that can persist lint-ignore rules. Project ignore rules match all populated `rule`, `source`, and `file` fields; an empty rule matches nothing. The complete rule format is included in the [Configuration reference](/docs/configuration-reference).

## Runtime settings

```yaml
lint:
  runtime:
    timeout: 3m
    mem: 1GiB
  linters:
    eslint:
      args: ["--max-warnings=0"]
    jscpd:
      enabled: true
```

Within a config layer, `runtime` precedes `lint.runtime`, which precedes `lint.linters.<name>.runtime`; later config layers and explicit invocation options win. `args` supplies native arguments, and `enabled` forces a tool on or off. `gavel lint --timeout 2m` sets a deadline for each linter invocation. Use `--no-lint-cache` to bypass result caching during diagnosis.

Secret-scanning rules stay in `.betterleaks.toml` or `.gitleaks.toml`. Gavel discovers and merges those files; `secrets.configs` names additional files, and `secrets.disabled` controls scanner activation.

## Report and combine with tests

```bash
mkdir -p .tmp
gavel lint --summary --summary-limit 3
gavel lint --format "json=.tmp/lint.json,markdown=.tmp/lint.md"
gavel lint --ui --addr localhost
gavel test --lint --format "json=.tmp/checks.json,html=.tmp/checks.html"
```

Summary output groups findings by linter and rule with a limited set of example locations. JSON retains structured detail. Combined test runs include `lint_results` in the test snapshot. See [Reporting](/docs/reporting) for the distinction between standalone lint JSON and combined test JSON, and [Runner steps](/docs/fixture-runner-steps) to use lint as a fixture gate.
