The todo engine is Gavel's task execution layer. It turns work items into structured agent runs, records status, persists session metadata, and connects acceptance criteria to verification.

```bash
gavel todos list
gavel todos create "Fix flaky parser" # [!code highlight] [!code note:create issue]
gavel todos get 90ec80f0 # [!code word:90ec80f0]
gavel todos run 90ec80f0 # [!code focus] [!code note:agent loop]
gavel todos check 90ec80f0 # [!code info] [!code note:definition of done]
```

Line 1 lists active work. Line 2 creates a native PostgreSQL issue. Line 3 prints the full todo body, status, event history, and parsed sections. Line 4 starts the agent loop. Line 5 re-runs the issue's fixture/CEL definition of done.

`gavel todo` is an alias for `gavel todos`.

## Storage and portable files

<DocChildren parent="todo-engine" />

TODO commands require a configured PostgreSQL workspace. Set `GAVEL_DB_DSN` to your development database connection string, use the global `--db-url` option, or configure managed local PostgreSQL with `gavel system install --embedded`. The install command writes local database/service configuration and starts a user-level background service; it can download PostgreSQL binaries on first use. Inspect `gavel system install --help` before choosing this setup.

Run `gavel serve` once against that development database to apply schema migrations. Ordinary TODO commands open the workspace without migrating it. If a binary upgrade reports `database schema is behind this binary`, run the migration-serving command again before listing or editing TODOs. AI planning and implementation also require a configured Captain runtime, for example through `captain configure`.

PostgreSQL is the only runtime TODO store. List, create, run, check, and UI/API
operations always resolve the native database workspace; they do not inspect
`.todos`, provider flags, or project settings to choose a backend.

`.todos` Markdown remains available as an explicit portable interchange format:

```bash
gavel todos import                         # read .todos into PostgreSQL
gavel todos import --dir ./archive/todos # [!code focus]
gavel todos export                        # write PostgreSQL TODOs to .todos
gavel todos export 3f2a1b --dir ./backup # [!code highlight]
```

Import accepts explicit file arguments, or discovers Markdown below `--dir` when
none are supplied. Export accepts native IDs, short IDs, or imported aliases, or
exports the current workspace when none are supplied. Relative directories are
resolved beneath the selected working directory. Neither command enables a file
runtime provider.

The portable contract round-trips native ID, title, Markdown body (including
acceptance criteria and verification fixtures), labels, `low`/`medium`/`high`
priority, and `draft`/`pending`/`verified`/`completed` status. Captain execution
state, event history, plan and prompt-run links, arbitrary front matter,
`critical` priority, and `cancelled` status are database-owned. Arbitrary
front-matter keys are outside the portable contract and ignored on import;
non-representable priority/status values fail instead of being flattened.

## Creating todos

```bash
gavel todos create "Fix parser error messages"
gavel todos new --title "Add fixture docs" --body @todo.md # [!code focus] [!code note:full body]
gavel todos create --priority high --status pending "Stop leaking stderr"
gavel todos create "Fix parser" --plan @plan.md --verification @verification.md
gavel todos create "Fix parser" --plan @plan.md --status approved # [!code highlight] [!code note:ready to run]
```

Line 1 is the shortest path: the title comes from positional arguments. Line 2
uses the `new` alias and reads a full markdown body from a file. Line 3 sets
priority and initial status explicitly. Line 4 creates a durable Captain plan
awaiting review plus a persisted definition-of-done fixture. Line 5 records the
supplied plan as reviewed and approved, leaving the todo pending and ready for
`todos run`.

`--body`, `--plan`, and `--verification` accept inline text or an `@path` file
reference. Relative paths resolve from `--cwd`; prefix a literal leading `@`
with a backslash. `todos edit --body` and `todos comment --body` use the same
file-reference syntax.

Verification input is fixture markdown without an outer `## Verification`
heading. It can contain command blocks, Markdown tables, CEL assertions, or
`yaml test` / `yaml lint` fences. Run `gavel fixtures --help` for the complete
fixture format and available runner keys.

A top-level `# Verification` or `## Verification` section in `--body` is moved
out of the issue body and stored as dedicated verification markdown. When
`--verification` is also supplied, its content comes first and the fixture
extracted from the body is appended.

Create defaults:

- priority: `medium`
- status: `pending`
- storage: native PostgreSQL
- supplied plan approval: pending review
- verification: omitted unless `--verification` or a top-level H1/H2 body section supplies it

## Statuses

Todos use these statuses:

| Status | Meaning |
|--------|---------|
| `draft` | not ready to run |
| `pending` | ready, not started |
| `in_progress` | currently running |
| `review` | a plan is waiting for human approval |
| `ask` | the agent is blocked on questions |
| `verified` | the run met its definition of done |
| `unverified` | implementation finished but checks still failed |
| `completed` | finished without a definition-of-done gate |
| `failed` | execution failed |
| `skipped` | reproduction steps already pass |

`gavel todos list` hides verified and completed TODOs by default. Pass `--done` to include them. `--all` lists every registered project; combine it with `--done` when you need completed work across projects. Child TODOs are shown beneath their parent unless `--children` or `--parent` is supplied.

## Find and maintain work

```bash
gavel todos list --status pending
gavel todos list --all --done
gavel todos list --parent 90ec80f0
gavel todos get 90ec80f0
gavel todos criteria 90ec80f0
gavel todos edit 90ec80f0 --priority high --label parser --label bug
gavel todos edit 90ec80f0 --verification @verification.md
gavel todos comment 90ec80f0 --body @checkpoint.md
gavel todos reopen 90ec80f0
```

Replace example references with a TODO's short ID, full ID, title, or imported alias. `get` shows its body, lifecycle state, and children. `criteria` inspects the acceptance criteria. Edits and comments persist immediately; `reopen` makes finished work eligible for another lifecycle run. Supplying `--label` replaces the label set, and `--clear-labels` removes it.

## Sync source comments

```bash
gavel todos sync --dry-run ./pkg
gavel todos sync ./pkg
gavel todos sync --markers TODO,FIXME --ignore "**/generated/**"
```

Sync turns source TODO/FIXME comments into native issues while retaining their source location. Inspect the dry-run before syncing a large repository. Explicit import/export remains the route for portable `.todos` Markdown; runtime listing and execution use PostgreSQL.

## Portable todo front matter

Files used by the explicit import/export commands use YAML front matter. Runtime
commands do not read these fields directly.

```yaml
---
title: Fix parser error messages
priority: high
status: pending
id: 90ec80f0-1111-4222-8333-444444444444 # [!code focus]
labels: [parser, bug]
---
```

`id` lets a later import update the same native issue. Older files without an ID
receive a stable workspace-and-relative-path-derived native ID. Fields outside
the portable contract are not runtime configuration.

## Sections

A todo body can include normal markdown plus structured sections:

- `## Steps To Reproduce` as fixture nodes used for the pre-check.
- `## Acceptance Criteria` as editable done-ness criteria.
- `## Verification` as fixture nodes used by the run loop.
- comments, native issue events, latest failure, attempts, and verification results.

The todo engine deliberately reuses fixture parsing for verification sections. That keeps command checks, test/lint runner steps, and AI review in one format.

## Verification results

Every definition-of-done evaluation is persisted with the prompt run that produced it — both an explicit `gavel todos check` and the in-loop check a `gavel todos run` performs. The dashboard's **Verification** tab lists those attempts newest-first, so a failed check survives a reload, and its tab badge turns red while the latest attempt is failing.

Each attempt exposes its evidence through four sub-tabs:

- **Test** and **Lint** — the results of a `yaml test` / `yaml lint` runner step. The recorded counts and top failures render immediately; the full tree is read from the run's `.gavel/run-*.json` artifact.
- **Session** — the agent transcript, when the attempt ran one.
- **Output** — every other step (`exec`, `bash`, `ai`) with its command, exit code, ANSI-rendered streams and, for a failing step, the CEL expression and the values it saw — plus the acceptance-criteria checklist.

A failure that happens *before* execution starts — no verification fixture, no acceptance criteria, no configured checks — creates no prompt run, so it is reported inline on the tab instead of being listed as an attempt.

## Write an executable definition of done

Keep product outcomes in the task body and runnable evidence in the verification fixture. For example, create `todo.md` with the concrete error and acceptance criteria:

```markdown
# Fix parser error messages

Invalid input currently produces an error without a source position.

## Acceptance Criteria

- [ ] Invalid input reports its line and column.
- [ ] Valid input preserves its parsed result.
```

Create `verification.md` with test and lint gates appropriate to the repository:

````markdown
### Parser regressions

```yaml test
paths: [./pkg/parser]
framework: [go]
test-timeout: 2m
```

### Source checks

```yaml lint
files: [./pkg/parser]
linters: [golangci-lint]
timeout: 2m
```
````

```bash
gavel todos create --title "Fix parser error messages" --body @todo.md --verification @verification.md
gavel todos check 90ec80f0
```

Use paths and tools that exist in your project. The fixture is persisted separately from the issue body and reused for standalone checks and implementation feedback. Acceptance-criteria grading is part of that definition of done and uses the verification runtime. A check can execute commands and a grader, but it does not start an implementation turn.

## Plan, review, implement, and verify

```bash
gavel todos steps 90ec80f0
gavel todos run 90ec80f0 --step plan --dry-run
gavel todos run 90ec80f0 --step plan
gavel todos plan show 90ec80f0
gavel todos plan approve 90ec80f0
gavel todos run 90ec80f0 --step run
gavel todos check 90ec80f0
```

Planning creates a durable plan for review. Approval makes it eligible for implementation; `plan approve --run` also starts implementation immediately. Use `gavel todos plan revise 90ec80f0 --feedback "Add the invalid-input case"` to request changes, or `gavel todos plan reject 90ec80f0` to return it to pending. The built-in implementation step uses an isolated worktree and declares automatic commits. `--commit=false` is rejected for a step whose resolved workflow declares commits; inspect the workflow before dispatching.

See [Todo run loop](/docs/todo-run-loop) for step selection, worktrees, resumable sessions, result envelopes, and feedback budgets. [Runtime presets](/docs/todo-runtime-profiles) covers model and permission defaults, and [Reporting](/docs/reporting) explains the run artifacts linked from verification results.
