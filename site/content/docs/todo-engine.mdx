The todo engine is Gavel's task execution layer. It turns work items into structured agent runs, records status, persists session metadata, and connects acceptance criteria to verification.

```bash
gavel todos list
gavel todos create "Fix flaky parser" # [!code highlight] [!code note:create issue]
gavel todos get 90ec80f0 # [!code word:90ec80f0]
gavel todos run 90ec80f0 # [!code focus] [!code note:agent loop]
gavel todos check 90ec80f0 # [!code info] [!code note:definition of done]
```

Line 1 lists active work. Line 2 creates a native PostgreSQL issue. Line 3 prints the full todo body, status, event history, and parsed sections. Line 4 starts the agent loop. Line 5 re-runs the issue's fixture/CEL definition of done.

`gavel todo` is an alias for `gavel todos`.

## Storage and portable files

PostgreSQL is the only runtime TODO store. List, create, run, check, and UI/API
operations always resolve the native database workspace; they do not inspect
`.grite`, `.todos`, provider flags, or project settings to choose a backend.

`.todos` Markdown remains available as an explicit portable interchange format:

```bash
gavel todos import                         # read .todos into PostgreSQL
gavel todos import --dir ./archive/todos # [!code focus]
gavel todos export                        # write PostgreSQL TODOs to .todos
gavel todos export 3f2a1b --dir ./backup # [!code highlight]
```

Import accepts explicit file arguments, or discovers Markdown below `--dir` when
none are supplied. Export accepts native IDs, short IDs, or imported aliases, or
exports the current workspace when none are supplied. Relative directories are
resolved beneath the selected working directory. Neither command enables a file
runtime provider.

The portable contract round-trips native ID, title, Markdown body (including
acceptance criteria and verification fixtures), labels, `low`/`medium`/`high`
priority, and `draft`/`pending`/`verified`/`completed` status. Captain execution
state, event history, plan and prompt-run links, arbitrary front matter,
`critical` priority, and `cancelled` status are database-owned. Arbitrary
front-matter keys are outside the portable contract and ignored on import;
non-representable priority/status values fail instead of being flattened.

## Creating todos

```bash
gavel todos create "Fix parser error messages"
gavel todos new --title "Add fixture docs" --body-file todo.md # [!code focus] [!code note:full body]
gavel todos create --priority high --status pending "Stop leaking stderr"
```

Line 1 is the shortest path: the title comes from positional arguments. Line 2 uses the `new` alias and reads a full markdown body from a file. Line 3 sets priority and initial status explicitly.

Create defaults:

- priority: `medium`
- status: `pending`
- storage: native PostgreSQL
- acceptance criteria generation: enabled when a model is available

Use `--criteria=false` to skip AI-drafted acceptance criteria. Use `--model` to choose the model for criteria generation.

## Statuses

Todos use these statuses:

| Status | Meaning |
|--------|---------|
| `draft` | not ready to run |
| `pending` | ready, not started |
| `in_progress` | currently running |
| `review` | a plan is waiting for human approval |
| `ask` | the agent is blocked on questions |
| `verified` | the run met its definition of done |
| `unverified` | implementation finished but checks still failed |
| `completed` | finished without a definition-of-done gate |
| `failed` | execution failed |
| `skipped` | reproduction steps already pass |

`gavel todos list` hides completed todos by default. Pass `--all` to include them.

## Portable todo front matter

Files used by the explicit import/export commands use YAML front matter. Runtime
commands do not read these fields directly.

```yaml
---
title: Fix parser error messages
priority: high
status: pending
id: 90ec80f0-1111-4222-8333-444444444444 # [!code focus]
labels: [parser, bug]
---
```

`id` lets a later import update the same native issue. Older files without an ID
receive a stable workspace-and-relative-path-derived native ID. Fields outside
the portable contract are not runtime configuration.

## Sections

A todo body can include normal markdown plus structured sections:

- `## Steps To Reproduce` as fixture nodes used for the pre-check.
- `## Acceptance Criteria` as editable done-ness criteria.
- `## Verification` as fixture nodes used by the run loop.
- comments, native issue events, latest failure, attempts, and verification results.

The todo engine deliberately reuses fixture parsing for verification sections. That keeps command checks, test/lint runner steps, and AI review in one format.
