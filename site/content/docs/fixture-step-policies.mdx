Every typed step has a common envelope alongside its kind-specific fields. These controls describe how execution is named, asserted, observed, and shared with later steps.

| Field | Behavior |
| --- | --- |
| `kind` | Required registered kind, such as `exec`, `services`, or `test` |
| `id` | Reference name for later `steps.<id>` CEL expressions |
| `name` | Human-readable result label |
| `cel` | Verdict over current outputs, environment, and earlier step results |
| `export` | Environment names mapped to templates over outputs |
| `override` | Explicitly permit replacing an earlier export |
| `background` | Keep a supported kind running through fixture teardown |
| `continueOnError` | Report the step's failure without skipping later steps. By default a failed step skips every step after it, because each may depend on it; set this on steps nothing later depends on, such as independent renders after a shared setup |
| `timeout` | Execution deadline |
| `wait` | Poll observable state until a verdict or deadline |
| `retry` | Repeat execution when its configured failed-result predicate holds |

## Outputs and exports

```yaml
kind: Fixture
steps:
  - id: first
    kind: exec
    exec: printf
    args: ["%s", "ready"]
    export:
      MESSAGE: "{{.outputs.stdout}}"
  - id: second
    kind: exec
    exec: printf
    args: ["%s", "{{.env.MESSAGE}}"]
    cel: stdout == steps.first.stdout && stdout == "ready"
```

Exports reach later steps. Re-exporting a name requires `override: true`. The `"*"` key exports an output map; an empty export value suppresses a kind's default export. A step's own environment declarations take precedence over values inherited from exports.

Use `{{.env.NAME}}` to substitute an earlier export in a directly executed argument. A shell script can instead expand `$NAME` from its environment. [Download the runnable export example](/examples/step-exports.fixture.yaml).

## Wait versus retry

`wait.until` polls a kind's observation method. `failWhen` ends polling early. A wait can inspect a running service or rerun a safe command probe, depending on the kind. Kinds without observation reject waits.

`retry.when` evaluates over a failed Execute result and decides whether to execute again. `attempts`, delay, backoff, and jitter bound retries. Wait and CEL evaluation occur afterward; failing those checks does not trigger another Execute attempt. Polling an existing resource and repeating a write are materially different; select the mechanism that matches the kind.

## Lifetime and teardown

`background: true` is for kinds supporting work that remains active while later steps execute. Teardown collects its verdict and releases resources. Kind-specific startup/readiness deadlines are separate from the overall step deadline. See [Services](/docs/fixture-kind-services), [Browser](/docs/fixture-kind-browser), and [Playwright](/docs/fixture-kind-playwright) for their lifetime contracts.
