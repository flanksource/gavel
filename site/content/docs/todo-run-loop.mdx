`gavel todos run` is an agent loop around one or more todos. It selects work, chooses an agent driver, records session state, and maps the agent's structured result back onto todo status.

```bash
gavel todos run 90ec80f0
gavel todos run --mode plan 90ec80f0 # [!code highlight] [!code note:reviewable plan]
gavel todos run --check --commit 90ec80f0 # [!code focus] [!code note:full loop]
gavel todos check 90ec80f0 # [!code info] [!code note:manual definition of done]
```

Line 1 runs the default implementation mode. Line 2 asks the agent to produce a reviewable plan. Line 3 runs implementation, fixture-backed checks, and auto-commit as one workflow. Line 4 re-runs the same definition of done without an implementation agent.

## Modes

`--mode` selects the operation:

| Mode | Behavior |
|------|----------|
| `run` | implement the todo |
| `plan` | investigate and produce or revise a reviewable plan |

Plan mode is read-oriented. A completed plan run reports a native plan file path and moves the todo to `review` when the plan is new or updated. If the existing plan is unchanged, the todo returns to `pending`. If the agent needs input, the todo becomes `ask`.

## Drivers and sessions

Drivers choose how the agent runs. The default is a cmux-backed driver for the resolved agent. Explicit drivers include values such as `claude-cmux`, `claude-headless`, `codex-cmux`, and `codex-headless`. For Codex, `codex-headless` resolves to the `codex-agent` app-server backend.

```bash
gavel todos run --driver claude-cmux --model claude-code-sonnet 90ec80f0 # [!code focus]
gavel todos run --resume 90ec80f0 # [!code highlight] [!code note:same session]
```

Line 1 pins both the driver mechanism and the model. Line 2 resumes the prior recorded session instead of starting a new one, which is the right path for answering questions or continuing interrupted work.

Gavel records session IDs on the todo so later runs can resume or focus the same work. A todo in `ask` stores the agent's blocking questions; answering resumes the prior session and applies the same result mapping.

## Result envelopes

Every agent run is expected to finish with a structured envelope:

```json
{
  "summary": "What changed or what blocked progress.",
  "endStatus": "completed", // [!code focus] [!code note:status mapping]
  "questions": []
}
```

`summary` is persisted as the last-run summary. `endStatus` drives the status transition. `questions` is only meaningful when `endStatus` is `ask`; otherwise Gavel clears stale questions.

Plan mode adds a `plan` object:

```json
{
  "summary": "Investigated the parser and wrote a plan.",
  "endStatus": "completed",
  "plan": {
    "status": "new", // [!code focus] [!code note:new updated unchanged]
    "path": "/absolute/path/to/plan.md" // [!code warning]
  }
}
```

The `plan.status` value tells Gavel whether the plan is new, updated, or unchanged. A new or updated plan must include an absolute `plan.path`; Gavel validates that file before moving the todo to `review`.

The envelope drives status transitions:

- `ask` becomes `ask` and persists questions.
- plan `new` or `updated` becomes `review`.
- plan `unchanged` becomes `pending`.
- a run with passing definition-of-done verifiers becomes `verified`.
- a run whose definition-of-done still fails becomes `unverified`.
- a run with no definition-of-done gate becomes `completed`.

## Checks

The `--check` flag enables the post-completion test/lint loop. Project defaults live in `.gavel.yaml`; a todo's front matter can override them.

```yaml
checks:
  enabled: true # [!code focus]
  maxIterations: 3 # [!code warning] [!code note:retry budget]
  test:
    changed: true
    timeout: 5m
  lint:
    changed: true
    timeout: 5m
```

Lines 2-3 turn on the loop and cap retries. Lines 4-9 define the test and lint fixtures Gavel will run after the agent reports completion. `changed: true` keeps feedback focused on work affected by the run.

When checks fail, Gavel feeds a compact failure summary back to the same agent session. The loop continues until checks pass or the iteration budget is exhausted.

Under the hood, checks are fixture runner steps: Gavel marshals the resolved test/lint options into the same shape as a `yaml test` or `yaml lint` fence and runs them through the fixture engine.

## Verification fixture

A todo's `## Verification` section is its definition of done. It runs even when `checks.enabled` is false.

````markdown
## Verification

### command: parser reports actionable errors

```bash
gavel fixtures fixtures/parser-errors.fixture.md # [!code focus] [!code note:existing suite]
```

- cel: exitCode == 0 # [!code info]

### command: changed packages pass

```yaml test
changed: true # [!code highlight]
framework: [go]
test-timeout: 2m
```
````

Line 1 names the section Gavel parses as verification fixtures. Lines 5-9 run an existing fixture suite and require it to pass. Lines 13-17 run changed Go tests through the fixture runner step. Because this section is the definition of done, failures become agent feedback and determine whether the todo ends as `verified` or `unverified`.

The verification fixture is evaluated inside the agent loop. Passing nodes promote the todo to `verified`; failures become feedback for the next iteration or leave the todo `unverified` when the budget runs out.

## Commit and manual verification

`--commit` is enabled by default for implementation runs. When the executor did not already commit, Gavel runs the same commit pipeline as `gavel commit` over the agent's changes.

`gavel todos check` runs the same fixture/CEL definition of done on demand and
records the resulting verified or unverified lifecycle state.

```bash
gavel todos run --commit=true --check 90ec80f0 # [!code focus]
gavel todos check 90ec80f0 # [!code warning]
```

The first command feeds failing checks back into the implementation loop before
committing successful work. The second command can be run later without starting
an implementation agent.
