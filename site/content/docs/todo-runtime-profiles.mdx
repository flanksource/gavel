Runtime presets provide reusable Captain specs: model selection, budgets, permissions, setup, memory, tools, and sandbox configuration. Gavel selects an ordered list of presets, then combines their layers with project settings, prompt defaults, the TODO, and explicit request fields.

## Preview and select presets

Replace `90ec80f0` with an existing TODO reference and preset names with records available in your Captain catalog:

```bash
gavel todos run 90ec80f0 --step plan --preset bounded-work --dry-run
gavel todos run 90ec80f0 --step run --preset bounded-work --preset project-work
gavel todos run 90ec80f0 --step plan --no-presets --dry-run
```

The dry-run prints selected presets, the rendered prompt, the ordered layer trace, and the resolved spec without dispatching. Repeating `--preset` layers records in the supplied order. `--no-presets` clears inherited selections and cannot be combined with `--preset`. Unknown or ambiguous names fail; use a unique name or catalog ID.

Selecting presets and overriding their fields are separate operations. An explicit `--model cli:opus:high` supplies a request override; inspect the trace to confirm the effective model, budget, and permissions. A dry-run previews resolution, while runtime startup validates the selected backend's capabilities.

## Catalog sources

Gavel uses Captain's shared catalog for the selected workspace:

| Source | Location |
| --- | --- |
| Database records | Captain records in the TODO workspace database |
| User files | `~/.config/captain/presets/*.yaml` |
| Configured directories | Captain configuration's `runtime.presetDirs` |
| Repository files | `.captain/presets/*.yaml` beneath the selected working directory |
| Embedded records | Presets supplied by the runtime or host |

`XDG_CONFIG_HOME` changes the user config base. Configured relative directories resolve against Captain's configuration directory. Configured directories must exist; missing implicit user/repository directories are allowed. File discovery reads immediate `.yaml` children. File records derive their IDs from source and filename, so omit `id`.

For example, create `.captain/presets/bounded-work.yaml`:

```yaml
name: bounded-work
description: Limits for project work
scope: global
spec:
  budget:
    maxTurns: 30
    timeout: 20m
```

Create a separate `.captain/presets/project-work.yaml` when model selection should be reusable:

```yaml
name: project-work
description: Implementation model for this project
scope: global
spec:
  model: cli:opus:high
```

Captain preset files wrap runtime fields in `spec`. Gavel's per-step config uses flat spec fields.

## Configure project and step defaults

```yaml
todos:
  presets: [bounded-work, project-work]
  plan:
    presets: [bounded-work]
    model: cli:opus:high
  run:
    budget:
      maxTurns: 40
    workflow:
      verify:
        maxIterations: 3
```

`run` inherits the project list; `plan` selects its own list and supplies its model directly. An explicit `presets: []` on a step clears the project list for that step. Custom lifecycle steps use `todos.steps.<name>.presets`; built-ins keep their dedicated blocks.

A complete `.prompt` file can pin a list with top-level frontmatter `presets: [bounded-work]`. Keep its existing input variables and result envelope when changing the prompt. See [Prompt overrides](/docs/prompt-overrides).

## Selection and value precedence

The selected preset list comes from the first explicit source:

1. CLI `--preset` / `--no-presets`, or HTTP `presets`.
2. Prompt frontmatter `presets`.
3. Step configuration `presets`.
4. Project `todos.presets`.
5. No presets.

An explicit empty list is a selection. Lists at different selection levels are not concatenated. Selected presets then participate in Captain's layer ordering, with scopes `global`, `context`, `surface`, and `user`. Within a scope, later layers naming a field take precedence. Use `scope: global` for reusable defaults that prompts and requests should be able to refine.

The run trace records project AI defaults, selected presets, prompt frontmatter, lifecycle step specs, project step overrides, TODO-specific configuration, continuations, host settings, and explicit request fields. Planning, triage, and verification retain their enforced execution posture after resolution.

HTTP callers send preset selection beside explicit spec overrides:

```json
{
  "ref": "90ec80f0",
  "step": "plan",
  "presets": ["bounded-work"],
  "spec": {
    "budget": { "maxTurns": 8 }
  }
}
```

Send only fields the caller explicitly changes in `spec`. Copying a previously resolved model into the request would override a newly selected preset's model.

## Verification runtime

Standalone AI fixtures resolve grader defaults through `todos.verify` over the base `ai` spec. A document's own `ai` configuration takes precedence. A complete `ai.spec` snapshot replaces defaults and avoids resolving a catalog selection again, so an external fixture runner uses the runtime already selected by its caller.

Command-only fixtures do not need an AI preset catalog. See [AI review fixtures](/docs/fixture-ai-review) for the grader snapshot contract and [Configuration reference](/docs/configuration-reference) for every spec field and referenced type.

## Migrate retired settings

| Retired setting | Replacement |
| --- | --- |
| `--runtime-profile` | Repeatable `--preset`, or `--no-presets` |
| `todos.runtimeProfile` / step `runtimeProfile` | Project or step `presets` list |
| Prompt frontmatter `runtimeProfile` | Prompt frontmatter `presets` |
| HTTP `runtimeProfile` | HTTP `presets` array |
| `todos run --driver` / `todos.driver` | Model selection such as `--model cli:opus:high` |
| Lifecycle selection through `todos run --mode` | `--step plan`, `--step run`, or a declared custom step |
| `todos.prompts` | `todos.lifecycle.steps` and `todos.steps.<name>` |
| `checks.maxIterations` | `todos.run.workflow.verify.maxIterations` |
| `permissions.presets` | Native permission mode and current Captain policy fields |

Profile selections are deprecated, warn, and contribute no layers. Replace them with preset records rather than copying a profile selection into another config surface. The built-in implementation prompt uses `permissions.mode: acceptEdits`; model and tool policies still need to match the selected runtime.
