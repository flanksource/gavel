Fixture files have their own schema, separate from `.gavel.yaml`. Markdown combines frontmatter, headings, tables, executable fences, and assertions. YAML and JSON use a typed `kind: Fixture` document. Both lower into the fixture runner's result tree.

<a href={schemaUrl} download="fixtures.schema.json">Download the complete fixture schema bundle</a>

This site bundles the output of `gavel fixtures --schema`, containing `frontmatter`, `document`, `fences`, and help metadata. Generate a bundle from your installed Gavel when its version differs:

```bash
mkdir -p .tmp
gavel fixtures --schema > .tmp/fixtures.schema.json
jq '.frontmatter' .tmp/fixtures.schema.json > .tmp/fixture-frontmatter.schema.json
jq '.document' .tmp/fixtures.schema.json > .tmp/fixture-document.schema.json
jq '.fences.test.schema' .tmp/fixtures.schema.json > .tmp/fixture-test.schema.json
```

The bundle is a container of schemas. Give an editor the extracted schema for the surface being edited. `.frontmatter` validates the YAML header of Markdown, `.document` validates a whole YAML/JSON fixture, and `.fences.<kind>.schema` validates that fence's configuration.

## Markdown frontmatter

````markdown
---
cwd: .
exec: bash
args: ["-c", "printf '%s\\n' '{{.message}}'"]
message: ready
timeout: 30s
---

# CLI checks

| Name | message | Exit Code | CEL Validation |
| --- | --- | --- | --- |
| Default message | | 0 | stdout.trim() == "ready" |
| Row override | done | 0 | stdout.trim() == "done" |
````

Frontmatter establishes defaults for the document. Unknown keys become template metadata, and table values can override them. `setup` prepares a shared environment before `build`; a `daemon` starts after the build and is stopped after execution. Tests in the same Markdown file share the setup, so use separate files when environments need isolation.

[Download a runnable Markdown example](/examples/smoke.fixture.md). It includes the table above and a JSON command assertion, and requires only Bash and `printf`.

Expand nested objects and lists to inspect their fields. Paths use `[]` for arrays and `<name>` for maps. Referenced Captain types open below the frontmatter hierarchy. For practical format choices, see [Fixture formats](/docs/fixture-formats).

## Command expectations

Command blocks may carry YAML configuration before an executable fence; fence attributes override that configuration. Expected `stdout` and `stderr` values can use `@path` golden-file references. In table fixtures, `exit code: -` disables exit-code checking; otherwise a successful exit is expected by default.

`contains:`, `regex:`, `not:`, and `cel:` bullets become assertions. Use `json` for parsed JSON output, `stdout` and `stderr` for streams, and `exitCode` for process status. PTY mode merges stdout and stderr; use it when terminal rendering or ANSI behavior is the subject of the check.

## Test runner fence

Use `yaml test` to invoke Gavel's test engine. Keys use CLI spelling such as `test-timeout`, with `paths` replacing positional CLI arguments. UI/detach options are excluded and fixture discovery does not recurse from these embedded steps.

<SchemaReference schema={schema.fences.test.schema} id="fixture-test" />

## Lint runner fence

Use `yaml lint` to invoke the lint engine. `files` replaces positional arguments. These steps report evidence inside the fixture tree; interactive triage and source-repair options are excluded from the embedded runner contract.

## AI prompt fence

The first `prompt` or `ai` fence supplies reviewer instructions. Configure the grader with `ai` frontmatter and its checklist with task-list items. See [AI review fixtures](/docs/fixture-ai-review) for scoring and grader configuration.
