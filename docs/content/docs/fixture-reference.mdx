Fixture files have their own schema, separate from `.gavel.yaml`. YAML and JSON use a typed `kind: Fixture` document with ordered steps. Markdown combines frontmatter, headings, tables, executable fences, and assertions. Both lower into the fixture runner's result tree; the examples default to YAML.

<a href={schemaUrl} download="fixtures.schema.json">Download the complete fixture schema bundle</a>

This site bundles the output of `gavel fixtures --schema`, containing `frontmatter`, `document`, `fences`, and help metadata. Generate a bundle from your installed Gavel when its version differs:

```bash
mkdir -p .tmp
gavel fixtures --schema > .tmp/fixtures.schema.json
jq '.frontmatter' .tmp/fixtures.schema.json > .tmp/fixture-frontmatter.schema.json
jq '.document' .tmp/fixtures.schema.json > .tmp/fixture-document.schema.json
jq '.fences.test.schema' .tmp/fixtures.schema.json > .tmp/fixture-test.schema.json
```

The bundle is a container of schemas. Give an editor the extracted schema for the surface being edited. `.frontmatter` validates the YAML header of Markdown, `.document` validates a whole YAML/JSON fixture, and `.fences.<kind>.schema` validates that fence's configuration.

## Markdown frontmatter

The YAML variant writes each command and its expectation as a step. The Markdown variant shares a command template in frontmatter and varies its input in table rows:

<FixtureExample>

```yaml
kind: Fixture
name: CLI checks
steps:
  - name: Default message
    exec: printf
    args: ["%s\n", "ready"]
    timeout: 30s
    cel: stdout.trim() == "ready"
  - name: Row override
    exec: printf
    args: ["%s\n", "done"]
    timeout: 30s
    cel: stdout.trim() == "done"
```

````markdown
---
cwd: .
exec: bash
args: ["-c", "printf '%s\\n' '{{.message}}'"]
message: ready
timeout: 30s
---

# CLI checks

| Name | message | Exit Code | CEL Validation |
| --- | --- | --- | --- |
| Default message | | 0 | stdout.trim() == "ready" |
| Row override | done | 0 | stdout.trim() == "done" |
````

</FixtureExample>

Frontmatter establishes defaults for the document. Unknown keys become template metadata, and table values can override them. `setup` prepares a shared environment before `build`; a `daemon` starts after the build and is stopped after execution. Tests in the same Markdown file share the setup, so use separate files when environments need isolation.

A setup that reads `{{.params.…}}`, or computes a value with `{$cel: …}`, is prepared after the `params` form answers rather than before `build`, so a run can pick its own cluster or credentials. Its environment then reaches every later step, and its connection references resolve through the same catalog a `format: connection` picker lists: the host, then the shared and gavel layers, then the fixture directory's `.connections/`. Because it is prepared after `build`, such a setup cannot declare `checkout:` or `cwd:`, and a fixture without `params:` cannot read them.

Under `connections:`, a string names that kind's connection, so `kubernetes: connection://acme` is `kubernetes: {connection: connection://acme}`. A picker commits exactly such a `connection://` reference. CEL is nil-safe, so a `$cel` reading an unanswered param is null, and a null connection is not configured at all. That is different from `kubernetes: {}`, which means the ambient cluster:

```yaml
kind: Fixture
params:
  type: object
  properties:
    scale: {type: boolean, default: true}
  allOf:
    - if: {properties: {scale: {const: true}}, required: [scale]}
      then:
        required: [k8s]
        properties:
          k8s: {type: string, format: connection, x-connection-types: [kubernetes]}
setup:
  connections:
    kubernetes: {$cel: "params.k8s"}   # null when scale is off: no cluster is configured
steps:
  - {id: nodes, kind: exec, if: params.scale, script: kubectl get nodes}   # the picked cluster's KUBECONFIG
```

## Command expectations

Command blocks may carry YAML configuration before an executable fence; fence attributes override that configuration. Expected `stdout` and `stderr` values can use `@path` golden-file references. In table fixtures, `exit code: -` disables exit-code checking; otherwise a successful exit is expected by default.

`contains:`, `regex:`, `not:`, and `cel:` bullets become assertions. Use `json` for parsed JSON output, `stdout` and `stderr` for streams, and `exitCode` for process status. PTY mode merges stdout and stderr; use it when terminal rendering or ANSI behavior is the subject of the check.

## Test runner fence

Use `kind: test` in a YAML document or `yaml test` in a Markdown fence to invoke Gavel's test engine. Keys use CLI spelling such as `test-timeout`, with `paths` replacing positional CLI arguments. UI/detach options are excluded and fixture discovery does not recurse from these embedded steps. [Runner steps](/docs/fixture-runner-steps) shows both formats.

## Lint runner fence

Use `kind: lint` in YAML or `yaml lint` in Markdown to invoke the lint engine. `files` replaces positional arguments. These steps report evidence inside the fixture tree; interactive triage and source-repair options are excluded from the embedded runner contract.

## AI prompt fence

Use `kind: ai` with `prompt` and `criteria` in YAML. In Markdown, the first `prompt` or `ai` fence supplies reviewer instructions; `ai` frontmatter configures the grader and task-list items supply the checklist. See [AI review fixtures](/docs/fixture-ai-review) for both formats and grader configuration.
