YAML fixtures declare `kind: Fixture` and ordered `steps`. Markdown fixtures use tables or executable code fences with optional YAML frontmatter. The paired examples show the same check in YAML first and Markdown second; save them as `.fixture.yaml` or `.fixture.md` and run `gavel fixtures <file>`.

The following defaults belong to Markdown frontmatter. File-level frontmatter sets defaults; table columns and command-block config override those defaults for individual tests. In YAML documents, use document `env`, step fields, and `defaults` instead; the Markdown `build` and `daemon` keys are not typed-document fields.

```yaml
---
build: go build -o myapp # [!code focus] [!code note:build once]
daemon: go run ./server --port {{.port}} # [!code focus] [!code word:{{.port}}]
exec: ./myapp # [!code highlight]
args: [--verbose] # [!code highlight]
env:
  LOG_LEVEL: debug
cwd: ./testdir
terminal: pty
timeout: 30s
os: linux
arch: amd64
skip: "! command -v docker" # [!code warning] [!code note:conditional skip]
---
```

Lines 2-3 run once for the file: `build` prepares the executable and `daemon` starts a background process that is stopped after the fixture run. Lines 4-7 define the default command shape for every test. Line 13 skips the file when its shell command exits successfully.

## Markdown tables

Use one YAML step per case. In Markdown, a table can share a command template and vary its inputs by row:

<FixtureExample>

```yaml
kind: Fixture
name: API checks
steps:
  - name: Get users
    exec: curl
    args: [-s, https://api.example.com/users]
    cel: json.size() > 0
  - name: Get health
    exec: curl
    args: [-s, https://api.example.com/health]
    cel: json.status == "ok"
```

````markdown
---
exec: bash
args: ["-c", "curl {{.flags}} {{.baseUrl}}{{.path}}"] # [!code word:{{.path}}] [!code note:row variable]
baseUrl: https://api.example.com
flags: "-s"
---

| Name       | path    | CEL                      |
|------------|---------|--------------------------|
| get users  | /users  | json.size() > 0          |
| get health | /health | json.status == "ok"      |
````

</FixtureExample>

The YAML variant supplies each URL and assertion directly. The Markdown variant defines the command template in frontmatter; `{{.flags}}`, `{{.baseUrl}}`, and `{{.path}}` supply its arguments. Each table row becomes a separate test. Replace `https://api.example.com` with your test API before running either variant.

Recognized input columns include `name`, `cli`, `command`, `exec`, `args`, `cwd`, `terminal`, `os`, `arch`, `skip`, and `query`.

Recognized expectation columns include `exit code`, `stdout`, `stderr`, `expected error`, `format`, `count`, `matches`, `files`, and `cel`.

Unrecognized columns become template variables and CEL properties. In the example above, `path` is available as `{{.path}}` in `args` and as `expectations.Properties["path"]` in CEL.

<Callout variant="tip" title="Compact Markdown cases">
  When using Markdown, a table keeps repeated command inputs and expectations together and gives each row its own result.
</Callout>

## Command blocks

Use a YAML `script` step for a multiline shell command, with its environment and assertion alongside it. In Markdown, use a command heading, optional configuration fence, and executable fence:

<FixtureExample>

```yaml
kind: Fixture
name: Multiline setup
steps:
  - kind: exec
    env:
      KEY: value
    script: |
      printf '%s\n' "hello"
      printf '%s\n' "$KEY"
    cel: stdout.contains("hello") && !stdout.contains("error") && exitCode == 0
```

````markdown
### command: multi-line setup

<!-- [!code highlight:4] -->
```yaml
exitCode: 0
env:
  KEY: value
```

```bash
printf '%s\n' "hello" # [!code focus] [!code note:produce stdout]
printf '%s\n' "$KEY"
```

- contains: hello
- not: contains: error
````

</FixtureExample>

Both variants set `KEY`, print two lines, and check stdout while rejecting unexpected error text. The YAML `cel` field holds the assertion; Markdown uses validation bullets after the Bash fence.

Validation bullets after a command are joined with `&&`:

- `cel: <expr>` uses the expression directly.
- `contains: <text>` checks stdout.
- `regex: <pattern>` checks stdout with a regular expression.
- `not: contains: <text>` negates a stdout contains check.
- `not: <expr>` negates a CEL expression.

## Standalone code blocks

Executable code blocks outside `command:` headings are auto-detected. The nearest heading becomes the test name.

<FixtureExample>

```yaml
kind: Fixture
name: Version output
steps:
  - exec: gavel
    args: [version]
    cel: stdout.matches("^gavel v") && exitCode == 0
```

````markdown
## Version output

```bash
gavel version # [!code focus] [!code note:test command]
```

- regex: ^gavel v # [!code highlight]
````

</FixtureExample>

The YAML variant names the executable and arguments explicitly. The Markdown heading names the test, the Bash fence runs it, and `regex:` checks stdout. Both expect a successful command whose output begins with `gavel v`.

Inline fence attributes override YAML block values:

<FixtureExample>

```yaml
kind: Fixture
steps:
  - kind: exec
    script: exit 1
    exitCode: 1
    timeout: 30s
```

````markdown
```bash exitCode=1 timeout=30
exit 1
```
````

</FixtureExample>

`exitCode: 1` in YAML and `exitCode=1` on the Markdown fence both expect a nonzero exit. YAML uses a duration such as `30s`; the Markdown fence attribute uses seconds.

## Variables and templates

`exec`, `daemon`, `build`, `args`, and `cwd` support shell-style variables and Go templates:

```yaml
exec: $executablePath
daemon: go run ./server --port {{.port}} # [!code word:{{.port}}]
args: ["--file", "$file"] # [!code word:$file]
build: make build
cwd: $GIT_ROOT_DIR/testdata # [!code word:$GIT_ROOT_DIR] [!code note:resolved before run]
```

`$executablePath` and `$workDir` come from the runner. `{{.port}}` is a free TCP port created for daemon fixtures. `$file` is available when `files:` expands a test across matched files. `cwd` is templated before Gavel resolves the final working directory. Point `exec` at the executable your build target actually produces.

Auto-injected variables are available in shell syntax, template syntax, CEL, and the command environment:

| Variable | Meaning |
|----------|---------|
| `GIT_ROOT_DIR` | nearest parent with `.git` |
| `GO_ROOT_DIR` | nearest parent with `go.mod` |
| `ROOT_DIR` | `GIT_ROOT_DIR`, then `GO_ROOT_DIR`, then workdir |
| `CWD` | resolved working directory for the test |
| `GOOS` / `GOARCH` | current Go runtime target |
| `GOPATH` | Go workspace path |

When `files:` is set, each matching file gets its own test expansion with `file`, `filename`, `dir`, `absfile`, `absdir`, `basename`, and `ext`.

## CEL context

CEL expressions can inspect:

- `stdout` or `output`
- `stderr`
- `exitCode`
- `json` when stdout starts with JSON
- `name`
- `sourceDir`
- `query`
- `expectations`
- `workDir`
- `executablePath`
- `ansi.has_color`, `ansi.has_any`, `ansi.has_updates`, and related terminal-state fields

Working directory resolution is deterministic: test-level `cwd`, file-level `cwd`, prepared setup directory, fixture source directory, then runner workdir or current directory. Relative paths resolve from the prepared setup when one exists, otherwise from the fixture source directory. Golden files resolve from the source directory even when commands run in a worktree.

## Golden files

Use `@path` in stdout or stderr expectations to compare against a file relative to the fixture source:

<FixtureExample>

```yaml
kind: Fixture
name: Golden output
steps:
  - name: Help contract
    exec: gavel
    args: [version]
    stdout: "@golden/version.txt"
```

````markdown
| Name | Command | Exit Code | Stdout |
| --- | --- | --- | --- |
| Help contract | gavel version | 0 | @golden/version.txt |
````

</FixtureExample>

Create the golden file with the expected output. Inspect a mismatch before updating it. When the output change is intentional, `gavel fixtures --update-golden checks.fixture.yaml` rewrites mismatched golden files; use `checks.fixture.md` for the Markdown variant. This command writes to the golden file.

## Traces and profiling

`traces:` arms commons-db trace kinds around a fixture. Every process the fixture starts — a command, a `services` entry, a browser — inherits the trace's exports, such as `HTTPS_PROXY` for a recording proxy, unless the setup, front matter or a step sets the variable itself. A `deps:` services entry passes them on only when deps runs the service as a host process (the binary and command runtimes), under the catalog's and the entry's own `env`; a docker or helm service never sees them, since a `127.0.0.1` proxy is unreachable from a container. Each kind's summary of the fixture's window becomes the CEL root named by the kind, and the records stay in the run's store under `.gavel/traces/<run>`, where the newest 20 runs are kept. A root of a trace the fixture did not arm is absent, so an assertion cannot treat an untraced request count as zero.

<FixtureExample>

```yaml
kind: Fixture
name: API trace
traces:
  - kind: http_proxy
    params: {mode: mitm, hosts: ["api.example.com"]}
    scope: test
    require: count > 0
  - kind: terminal
steps:
  - exec: curl
    args: [-sS, -o, /dev/null, https://api.example.com/health]
    cel: http_proxy.entries == 1 && terminal.exit_code == 0
```

````markdown
---
traces:
  - kind: http_proxy        # a recording proxy every child is pointed at
    params: {mode: mitm, hosts: ["api.example.com"]}
    scope: test             # test (default) | file | run
    require: count > 0      # CEL over the kind's summary; false fails a passing fixture
  - kind: terminal          # runs the command under a PTY and records it
---

# Calls the API

| Name  | Command                                    | CEL                                                         |
| ----- | ------------------------------------------ | ----------------------------------------------------------- |
| fetch | curl -sS -o /dev/null https://api.example.com/health | http_proxy.entries == 1 && terminal.exit_code == 0 |
````

</FixtureExample>

| Kind | What it records | CEL root keys |
| --- | --- | --- |
| `http_proxy` | Every exchange a child sends through a recording proxy (`mode: connect` records TLS tunnels, `mitm` decrypts them with an ephemeral CA the child is told to trust, and verifies the upstream against the system roots plus an `upstreamCA` PEM file; one it does not trust is answered 502 and recorded with its `error`) | `entries`, `errors`, `hosts`, `methods`, `statuses`, `requests[]` (with `query`, `body`, `response_body`, `response_json`), `tunnelled`, `bytes_in`, `bytes_out` |
| `pg_proxy` | Every statement a child runs through a postgres wire proxy in front of `dsn` (else the variable `env` names, else `GAVEL_DB_DSN`, `DATABASE_URL`); children get `DATABASE_URL`, `GAVEL_DB_DSN`, `PGHOST`/`PGPORT`/`PGUSER`/`PGDATABASE`/`PGSSLMODE` and the `env` variable pointing at the proxy, so `params: {env: APP_DB_URL}` observes an app that reads only `APP_DB_URL`. A named `env` that is unset is refused rather than replaced by `DATABASE_URL` | `statements`, `errors`, `duration_ms`, `by_op`, `tables`, `queries[]` |
| `terminal` | The command's PTY session; it implies `terminal: pty` and only command fixtures run under one | `exit_code`, `final`, `duplicates`, `has_duplicates`, `width`, `height`, `duration_ms`, `truncated` |
| `http` | gavel's own outbound HTTP (`features: [gavel]` by default) | as `http_proxy`, without the tunnel counts |
| `sql_statements` | gavel's own SQL (`connections: [self]` by default) | as `pg_proxy` |
| `process_tree`, `process_samples` | The processes under a root and their CPU and memory | `live`, `exited`, `peak_cpu_percent`, `peak_rss_bytes` |

Every summary has `count`, the window's records. A `test`-scoped trace is a capture of its own around the fixture; a `file` or `run` trace is one capture the file's or run's fixtures share, each windowed between marks taken before and after it, so concurrent rows of one file see each other's records there. A `Traces` table column takes the compact form (`http_proxy,terminal`, or `none`), and a fixture document takes `traces:` at the document or step level.

A `test`-scoped trace's `params` are templates rendered when its capture starts, like a step's config: `{{.env.X}}` reads the fixture Env, `{{.steps.<id>.…}}` an earlier step's outputs. So a proxy can front a service a previous step started on a port it allocated; templated params are validated once rendered. A `file` or `run` capture starts before any step runs, so its params cannot be templated.

```yaml
kind: Fixture
steps:
  - id: db
    kind: services
    services:
      pg:
        exec: ./start-postgres.sh {{.port}}
        ready: {tcp: "127.0.0.1:{{.port}}"}
  - id: migrate
    kind: exec
    traces:
      - kind: pg_proxy
        params: {dsn: "postgres://postgres@127.0.0.1:{{.steps.db.pg.port}}/postgres"}
        require: errors == 0
    script: psql "$DATABASE_URL" -f schema.sql
```

```bash
gavel fixtures --traces http_proxy --profile checks.fixture.yaml
gavel fixtures --benchmark --max-time 2s checks.fixture.yaml
```

`--traces` arms its kinds, test-scoped with default params, for every fixture that declares no `traces:` of its own; `traces: []` opts one out. The store also holds two kinds Gavel fills itself rather than a fixture arming them: `stacks` (goroutine and native stack dumps) and `goprof` (the Go profiles `goProfiles:` wrote under `--profile`, listed with the fixture's traces but not a CEL root). `--profile` reads the fixture process tree's CPU, memory and disk I/O from `process_tree`/`process_samples` and ingests declared Go profile outputs. `--benchmark` writes stage durations to `.gavel/benchmarks/fixtures/run-<timestamp>.json` and supports a saved baseline and regression limits. [Traces, profiling and benchmarks](/docs/traces-profiling-benchmarks) covers all three; the [Fixture file reference](/docs/fixture-reference) lists every `traces` and `goProfiles` option.
