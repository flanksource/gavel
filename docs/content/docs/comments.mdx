---
title: Comments and agent delivery
description: Send comment threads to Claude and Codex sessions, and send new comments to agents automatically.
---

Gavel stores comments made in `gavel edit`, the dashboard, `gavel launch serve` and the playground grabber. Each comment lives under a scope, such as `gavel://project/<name>` for a project, and its target URI sits beneath that scope (`.../files/<path>` for a file, `.../pages/<url>` for a web page).

## List comments for a file or directory

```bash
gavel comments list                      # every comment in the current directory's project
gavel comments list editor/store.go      # comments on one file
gavel comments list --path editor        # comments on every file under a directory
gavel comments list --scope gavel://project/gavel --target gavel://project/gavel/files/go.mod
```

The path is either a positional argument or `--path`, not both. Gavel resolves it to the most specific project holding it: a file lists its own threads, a directory lists the threads of every file beneath it, and the project root lists the whole scope. With neither a path nor `--scope`, the current directory is used. A path outside every project fails with `is not inside a gavel project`. `--phase`, `--unread`, `--limit` and `--offset` still apply. Over HTTP, pass `scope` (and optionally `target`); listing by path only works for the local tenant.

## Send a thread to an agent

Any open thread can be handed to an agent. Gavel assigns the thread to the agent, acknowledges it as the agent, and delivers it with the commands the agent uses to reply and resolve it. The hand-off is recorded on the thread as its `agentRun`: the session, when it was requested, its state (`queued`, `sent`, `done`, or `error` with the error), and where it went.

There are two kinds of target:

- **A live session.** The thread is delivered into a Claude or Codex session that is already running, through Captain.
- **A managed run.** Gavel starts or continues a session from a prompt (for example the library's `editor-comments`) in the project's directory. Comments in the same scope share a session by default, across pages. A group key selects a separate conversation. The session gets tools that list, reply to and resolve the threads on its target.

Comments arriving while a managed session is starting or working join the same conversation. Captain runs those turns in delivery order, retaining each comment's tools, permissions and outcome. A failed turn reports its error on the comment, including failures before the provider starts; it does not remain marked `queued`.

```sh
gavel comments deliver <id> --session <session-id>
gavel comments deliver <id> --prompt editor-comments
gavel comments deliver <id> --prompt editor-comments --group page:home --run-options '{"instructions":"Keep it short"}'
gavel comments deliver <id> --prompt editor-comments --group page:home --fresh
```

`--run-options` takes `presets`, `spec`, `variables` and `instructions`. Gavel always sets the `dir`, `scope`, `target`, `actor`, `gavelExecutable` and `message` variables itself.

`--fresh` always starts a new session, even when the group's session is still live. The new session becomes the group's, so later threads of the group go to it. It applies to `--prompt` only.

A failed delivery is recorded on the thread as an error and reported by the command, so the thread shows what went wrong. To retry, deliver the thread again (add `--fresh` to retry in a new session); the new hand-off replaces the recorded one.

The agent receives the thread with the context it was left in, whenever the comment has it: the page URL and title, the element's component and source file, the locators that find the element again, its HTML (trimmed to 4 KB), and links to the thread's attachments such as screenshots, followed by the comment and its replies.

## Send new comments to agents automatically

A comment agent sends every new comment on a file to an agent, without anyone choosing **Send to agent**. Only comments written by a person are sent; replies, review decisions and comments written by agents are not. Delivery runs in the background, so creating a comment never waits for it.

The Gavel extension enables **Auto-run new comments on this page** by default when you open an unconfigured page. It saves the page's agent in the project's database settings, so the choice survives closing the panel or reloading the page. Turning auto-run off saves an explicit opt-out and keeps the agent's other settings. An existing page or inherited setting with `enabled: false` stays off.

Comment agents are configured as `comments.agents` in the gavel settings of the file: the `.gavel.yaml` and `.gavel.<name>.yaml` files of your home directory, the project root and each folder down to the file, plus settings saved in the database where no file exists. A layer has a `default` agent for everything beneath its directory, and a `pages` map of agents for single files, keyed by path relative to the layer's directory:

```yaml
comments:
  agents:
    default:
      enabled: true
      prompt: editor-comments
    pages:
      16-security.mdx:
        assign: true
        instructions: Check every claim against the security controls.
```

Layers merge field by field, ancestors first, and within a layer its `default` then its page entry. `enabled: false` opts a folder or file out of an agent set further up. With `assign: true` the thread is assigned to the agent as soon as it is created. With `group: <key>` every thread the agent receives is delivered in that delivery group, separate from the scope's default shared session.

A delivery never gets in the way of the comment's author: attaching a screenshot right after creating the comment, with the version the create returned, succeeds while the agent picks the thread up.

A comment can also name where it goes when it is created: `deliver` on the create request is a delivery target (see [HTTP API](#http-api)) that replaces the comment agent for that comment, including its `assign`. The thread is delivered there once, in the background, even on a file no comment agent covers, and an invalid target fails the create before anything is stored. In the Gavel extension, the composer's target chip previews the page's comment agent while no target is chosen: **Auto: &lt;agent&gt;** when new comments are delivered to it, **Not delivered** when they are only posted. Pick `@session`, `@claude` or `@codex`, or type one in the comment, to send it elsewhere.

### Mentions

Without `deliver`, a person's comment or reply that mentions one agent is delivered to it, in the background, from every surface: the HTTP API, `gavel comments create --bodyMarkdown '@claude …'` and `gavel comments reply <id> --bodyMarkdown '@rename-pass …'` alike. The agents a comment can mention are listed by `GET /api/v1/comments/mentionables?scope=&target=`:

| Mention | Delivers to |
| --- | --- |
| `@agent` | The target's comment agent, whether or not it runs automatically, including its `assign`: an assigning agent becomes the thread's assignee before the delivery starts |
| `@<runtime family>` (`@claude`, `@codex`, …) | A fresh run of the family's default agent model, with the comment agent's prompt, presets, instructions, `edits` and `spec` (only the spec's model is replaced; the default prompt when no agent is configured) |
| `@<session slug>` | That live session, or an ended managed session of the scope, resumed. A session is named by its Captain slug; a managed session without one by its label (the thread it started for) as a slug, e.g. `@write-the-changelog`; any other by its id |

A mention is a whole `@name` token, matched case-insensitively: `@claudes` and `bob@claude.example` are not mentions, and a token that matches no agent is prose. A token in inline code (`` `@claude` ``), a fenced code block or a `>` blockquote is quoted text, not a mention. Mentioning two different agents fails the comment with 400 before it is stored, an explicit `deliver` wins over any mention, and an agent's own mentions are prose, so agents never hand threads to each other by quoting.

`@agent` and the runtime families are matched first and need no lookup; the scope's sessions are listed (from Captain) only when a token is still unmatched, so a comment mentioning `@claude` never waits on the session list. A scope without a local working directory, such as a web project with no folder on disk, has no session mentions: a `@<slug>` there is prose. `agent` and the runtime family names are reserved: a session whose slug collides with one is not listed, and two sessions sharing one slug are listed as `<slug>-<first 8 characters of the id>` rather than by the ambiguous name. A reply's mention inside `POST /api/v1/comments/batch` is delivered only after the batch commits; a batch that rolls back delivers nothing.

```sh
gavel comments agents set slides/16-security.mdx --layer slides --file .gavel.agents.yaml --page --prompt editor-comments --enabled
gavel comments agents set slides/16-security.mdx --layer project --file .gavel.yaml --enabled=false
gavel comments agents get slides/16-security.mdx
gavel comments agents delete slides/16-security.mdx --layer slides --file .gavel.agents.yaml --page
```

`--layer` is `user`, `project`, a folder relative to the project, or an absolute directory above it. `--file` names the config file to write (created when absent), or `--db` writes the database layer. `--page` edits the layer's entry for the file instead of its default. `set` replaces the whole entry with the fields its flags give, so a field no flag sets is removed and inherits again; `PUT /api/v1/comments/agent` patches an entry instead. `get` prints every layer and the agent that applies, each field traced to the layer that set it. For a web project, pass `--scope <scope-uri>` and the page key instead of a file path.

## Proposals

A reply can carry a proposed change instead of edits to your working tree, as Edit-tool-style `--edits` or a unified diff `--patch`. Gavel builds a commit on the repository's `HEAD` itself, in a temporary index that leaves your working tree and index untouched, and keeps it at `refs/gavel/comments/<thread>/<reply>`; the reply shows its state (`proposed`, `applied`, `staged`, `rejected`, `revision_requested` or `superseded`) and the files it changes. A newer proposal on the same thread supersedes the earlier one.

```sh
gavel comments reply <id> --expectedVersion <v> --bodyMarkdown 'Rename load to read' \
  --edits '[{"path":"src/app.go","oldString":"func load(","newString":"func read("}]'
gavel comments reply <id> --expectedVersion <v> --bodyMarkdown 'Rename load to read' --patch change.patch
git diff | gavel comments reply <id> --expectedVersion <v> --bodyMarkdown 'Rename load to read' --patch -
gavel comments accept-proposal <id> --expectedVersion <v> --messageId <reply> --mode apply
gavel comments reject-proposal <id> --expectedVersion <v> --messageId <reply> --bodyMarkdown 'Keep the old name'
gavel comments request-revision <id> --expectedVersion <v> --messageId <reply> --bodyMarkdown 'Keep the old name as an alias'
```

`--edits` is a JSON array applied in order, each edit one of:

| Edit | Effect |
| --- | --- |
| `{path, oldString, newString, replaceAll?}` | Replaces `oldString`, which must match the file exactly (whitespace included) once, or every match with `replaceAll` |
| `{path, content}` | Writes the whole file, creating it when missing |
| `{path, delete: true}` | Deletes the file |

Paths are relative to the repository root and cannot leave it or reach `.git`. Edits to one path apply to its content as the earlier ones left it, and a file keeps its mode (a new file is `100644`). A replacement that matches zero or several times, an edit of a missing file, or edits that change nothing are refused, naming the path. `--patch` takes a unified diff file instead, or `-` for stdin, whose `a/` and `b/` paths are relative to the repository root; a reply carries one or the other. `accept-proposal --mode apply` writes the patch into the working tree; `--mode stage` also stages it. A patch that no longer applies is a conflict. Asking for revisions sends the feedback back to the agent, which sees its earlier proposals and their feedback in the thread. `gavel comments list` shows `proposal: <state> · <n> files` under each reply that carries one.

Proposals are local only: a host without a local repository refuses them.

### Edits allowed or proposal-only

A comment agent's `edits` decides whether its agent may edit files:

```yaml
comments:
  agents:
    default:
      enabled: true
      edits: propose
```

`direct`, the default, lets the agent edit the project's files, reply and resolve the thread. `propose` tells the agent not to create or modify any file, not even scratch copies: it reads the files and replies with `--edits` (a managed session uses its `propose_change` tool, which takes the same `edits`), gavel builds the commit, and the agent is not offered a resolve command or tool, because a person accepts the proposal. While a thread's delivery is `propose`, an agent's resolve is refused until a proposal is accepted. The delivery records the policy as `edits` in the thread's `agentRun`.

Set it with `gavel comments agents set <path> ... --edits propose`, or for one delivery with `gavel comments deliver <id> --edits propose`. Every delivery that names no `edits` inherits the comment agent's, whether the agent runs automatically or not: a send to a live session, a batch, a mention, a retry and a preview alike (a batch whose threads' agents set different `edits` fails with 400 unless its target names one); without an agent, or one that sets no `edits`, it is `direct`. A managed run in propose mode cannot edit files: gavel denies its `Edit`, `Write`, `MultiEdit` and `NotebookEdit` tools over whatever the prompt allows (its shell stays available, under the same instruction). A live session is only instructed not to edit files: nothing stops it from doing so.

## HTTP API

Every host that serves `/api/v1/comments` also serves:

| Route | Body | Answer |
| --- | --- | --- |
| `GET /api/v1/comments?scope=[&target=][&after=]` | | Threads, each with `readVersion`, `unread` and, for a thread whose selector carries a patch, `anchor` (below) |
| `POST /api/v1/comments` | `{target, bodyMarkdown, workflowId, requestId, content?, links?, deliver?, attachments?}` | The new thread; `attachments` (below) are stored with it before it is delivered |
| `POST /api/v1/comments/read` | `{target: {scopeUri, uri}}` | Marks every thread on the target read for the caller at its current version: `{marked}`, the number not already read |
| `GET /api/v1/comments/agent-sessions[?scope=][&group=][&all=1]` | | Live and resumable managed sessions; `group` requires `scope` and returns only that group's current session |
| `GET /api/v1/comments/mentionables?scope=&target=` | | The agents a comment on `target` can mention: `[{id, name, kind: "agent"}]`, with ids `agent`, `runtime:<family>` and `session:<id>`; 501 on a host without agent delivery |
| `POST /api/v1/comments/{id}/deliver` | `{expectedVersion, requestId, target}` | The updated comment; 409 on a stale version, 502 when delivery failed |
| `POST /api/v1/comments/{id}/deliver/preview` | `{target}` | The resolved run and its tools, without starting it |
| `GET /api/v1/comments/agent?scope=&uri=` | | The target's comment agent: `{settings, agent, session?}`; `session` is the live session `gavel edit --session` routes every new human thread to, ahead of the agent |
| `PUT /api/v1/comments/agent` | `{target: {scopeUri, uri}, layer, page, agent}` | Patches the agent entry at a layer and answers `{settings, agent, session?}`; only a person can save one |
| `GET /api/v1/comments/{id}/proposals/{replyId}/diff` | | The reply's proposed patch: `{diff, commit, truncated?, binary?}` |

A target is `{kind: "session", sessionId}` or `{kind: "run", prompt, runOptions?, groupKey?, fresh?}`, either with `edits?` (`direct` or `propose`, inherited from the target's comment agent when omitted); `fresh` on a session target answers 400. Over HTTP an action's `patch` is the diff text itself, and its `edits` the same JSON array `--edits` takes. Retrying a hand-off is another `deliver` with the thread's latest version and a new `requestId`. With `scope`, the session listing shows only sessions working in that scope's project directory; `all=1` lists every live session.

`agent` on `PUT /api/v1/comments/agent` is a JSON merge patch (RFC 7386) of the entry the layer already holds for the page (or of its default with `page: false`), applied under the layer's save lock: a field that is present replaces that field (objects such as `variables` and `spec` merge), a field set to `null` is removed so it inherits again, and `agent: null` deletes the whole entry. `{"edits": "propose"}` changes only the policy; `{"instructions": null}` clears only the instructions. A patch naming an unknown field, a wrong type or an invalid `edits` answers 400 before anything is saved.

A listed thread's `anchor` is `{state, startLine?, endLine?}`: where its patch anchor lies in the target as it is now, resolved the same way `gavel edit` resolves it. `matched` carries the lines it now covers (moved when they differ from the patch's), `ambiguous` means the hunk now occurs more than once, and `outdated` means it no longer occurs. Only the host reads a target's content, once per target per request: a thread on a target kind it keeps no file content for (a web page) has no `anchor`, a file deleted since resolves `outdated`, and a target the host cannot read fails the list. `after=<id>` pages by thread id instead of `offset`, so a thread deleted between pages skips none after it.

A create's `attachments` are `[{filename, contentType, data}]`, at most 10, with `data` base64. They are stored on the new thread in the create's transaction, before it is routed, delivered or mentioned, so the agent sees them with the thread and no upload races the delivery's version bump. Each is checked first (a plain file name, a valid media type, 1 byte up to the host's attachment limit); an invalid one answers 400 before anything is written.

In the comment agent answer, `settings` is the target's layers and the positions of its chain (what can be saved where), and `agent` is the resolved agent, `{agent, provenance, found}`, with each field traced to the layer that set it. `layer` is `{kind: "user"|"parent"|"project"|"path", path?, file?}`; without `file` it saves the database layer. A host without settings-based comment agents answers 501, and a target its settings do not cover answers 400. On a project scope, both its files (`<scope>/files/<path>`) and its dashboard pages (`<scope>/pages/<page key>`) have comment agents; a page's agents live in the project's database layers (a page entry keyed `pages/<page key>` at the project layer), not in its `.gavel.yaml` files.

`gavel edit` also serves a file's comment agent settings: `GET /api/file/{id}/settings` answers its layers and the resolved agent with each field's layer, and `PUT /api/file/{id}/settings/agent` with `{layer, page, agent}` replaces the agent entry at a layer with `agent` (a null `agent` removes the entry) and answers the updated settings. Only a person can save one. Unlike `PUT /api/v1/comments/agent` it replaces rather than patches, because the editor sends the whole entry it rebuilt; both save through the same locked settings edit.

### Selectors in `gavel edit`

A file thread's `target.selector` is `{kind, version: 1, view, anchor?, patch?, quote?, region?, locators?, html?}`:

| Kind | On | Carries |
| --- | --- | --- |
| `document` | Any file | Nothing more: the whole file |
| `code-range` | Text files | `patch`, the exact capture of its source lines, from the `source`, `preview` or `rich` view; optionally `quote` |
| `dom` | Text files | `anchor` (the element), optionally `patch` and `quote` |
| `region` | Images | `region: {x, y, w, h}`, fractions of the image's width and height |

A `quote` is `{prefix?, exact, suffix?}`: source text as the file holds it (Markdown, not the rendered prose), with a non-empty `exact`. With a `patch`, `exact` must lie inside the patch's selected lines (CRLF compares as LF); a `dom` quote without a patch marks web text on a page without source. A `region` must be a non-empty box inside `[0,1]`: the server checks it strictly, so a client clamps a drag to the image before saving.
